# RIver AGI 最终验收前优化实施方案

## 一、当前结论

当前版本已经可以全新编译，`mvn clean test` 已通过 53 个测试，后端可以启动，RESTful API、JWT、上传、基础分析、图表、预测和标注基础接口已经存在。

但是以下问题仍阻断合同最终验收：安全扫描 500、解析任务错误处理不完整、质量分析重复检测不正确、生产静态前端与源码可能不是同一版本、权限覆盖不完整、生产密钥和加密配置不合格，以及性能、安全、覆盖率和交付文档没有验收证据。

最后一轮应定位为：修复 P0 缺陷、补齐合同验收证据、统一交付版本。

## 二、P0 必须优先修复

### P0-1 修复 H2 安全扫描数据库字段错误

现象：执行真实敏感数据扫描返回 HTTP 500，日志为：

```text
Column "TOTAL_FIELDS" not found
```

原因：`SecurityScanTask` 实体和 MyBatis 更新语句使用了 `total_fields`、`sensitive_fields_found` 等字段，但 `schema-h2.sql` 的 `security_scan_task` 表没有完整定义这些列。

具体方案：

1. 对照 `SecurityScanTask` 实体、Mapper SQL、MySQL schema 和 H2 schema，生成统一字段清单。
2. 在 `backend/src/main/resources/schema-h2.sql` 补齐：

```sql
total_fields INT DEFAULT 0,
sensitive_fields_found INT DEFAULT 0,
high_risk_count INT DEFAULT 0,
medium_risk_count INT DEFAULT 0,
low_risk_count INT DEFAULT 0
```

3. 在 MySQL Flyway 迁移脚本中补充同名字段，不能只修改 H2。
4. 删除旧 H2 测试库后重新启动，执行真实 Excel 安全扫描。
5. 验收必须确认：扫描返回 200、状态为 COMPLETED、风险记录可查询、手机号/身份证/邮箱/姓名/地址均能命中。
6. 增加 H2 和 MySQL 两套数据库集成测试，防止实体、Mapper 和表结构再次不一致。

### P0-2 修复异步解析任务闭环

现象：上传后后台解析可能最终完成，但手动调用 `/api/v1/datasets/{id}/parse` 返回 500，接口响应和后台任务状态不一致。

具体方案：

1. 上传接口只创建数据集和解析任务，统一返回 `taskId`。
2. 解析接口重复调用时执行幂等判断：已有 RUNNING/PENDING 任务时直接返回原 taskId；已 PARSED 时返回当前成功状态。
3. 统一任务状态：`PENDING`、`RUNNING`、`COMPLETED`、`FAILED`、`CANCELLED`。
4. 任务表必须记录：`progress_percent`、`started_at`、`finished_at`、`error_code`、`error_message`。
5. 后台成功时事务性更新数据集的行数、列数、schema、preview 和 status。
6. 失败时任务置为 FAILED，数据集置为 PARSE_FAILED，保存明确错误原因，不能返回泛化 500。
7. 增加以下测试：首次解析、重复解析、非法文件、空文件、解析失败、失败重试和任务取消。

### P0-3 修复质量分析的重复行检测

现象：测试文件存在重复记录，但返回 `duplicateRows=0`。

具体方案：

1. 读取完整数据行，不使用预览数据或前 10 行数据计算重复。
2. 使用固定字段顺序构造整行指纹：

```text
SHA-256(field1=value1|field2=value2|...)
```

3. 将同一指纹出现次数大于 1 的记录归为重复组。
4. 返回：

```json
{
  "duplicateRows": 2,
  "duplicateRowGroupsCount": 1,
  "duplicateRowGroups": [
    {"fingerprint":"...", "rowIndexes":[5,6]}
  ]
}
```

5. 明确区分“整行重复”和“主键重复”，两者分别统计。
6. 质量结果必须满足：`totalRows`、`totalCells`、`nullCells`、`emptyCells`、重复行数量和异常行数量可以复算。
7. 使用综合测试 Excel 增加断言：重复行必须大于 0，非法日期必须大于 0，负价格必须命中，需求量空值必须命中。

### P0-4 统一前端源码和生产静态资源

现象：项目存在多套前端目录；源码部分已经使用新接口，但 Spring Boot static 编译产物仍可能调用旧接口 `/api/v1/datasets/analyze` 和 `/api/v1/chat/ask`。

具体方案：

1. 明确唯一前端源目录，建议以 `frontend/` 为唯一源代码目录。
2. 删除或废弃 `backend/src/main/frontend` 中的旧首页，避免两套 App.vue 继续产生不同功能。
3. 统一 API 客户端，所有请求都经过同一个 request 封装，自动添加 JWT 和处理统一响应。
4. 图表字段不能写死为“日期/销售额”，必须使用后端推荐字段或用户选择字段。
5. 预测算法不能写死 `LIGHTGBM`，必须从 `/api/v1/predictions/algorithms` 动态读取实际支持算法。
6. 构建前端并将最新 dist 明确复制到 `backend/src/main/resources/static`。
7. 清空旧 static 资源后重新构建，检查最终 JS 中不能出现：

```text
/api/v1/datasets/analyze
/api/v1/chat/ask
LIGHTGBM
xAxisField=日期
yAxisField=销售额
```

8. 用浏览器完成上传、分析、图表和预测流程，不能只做后端测试。

### P0-5 完成真实安全扫描和脱敏验证

具体方案：

1. 安全扫描同时检查字段名和完整单元格内容。
2. 至少支持：手机号、身份证号、银行卡号、邮箱、姓名、地址、密码、薪资和收入。
3. 每条命中保存字段、敏感类型、命中数量、风险等级、置信度、规则版本、脱敏示例和整改建议。
4. 脱敏接口真实生成预览和文件，不能只返回 `COMPLETED`。
5. 对手机号、邮箱、身份证号和地址分别验证脱敏格式。
6. 扫描失败必须记录 FAILED 任务、错误码、错误信息和审计日志。
7. 安全扫描成功后，从风险查询接口和审计接口都能查到结果。

### P0-6 完成资源权限和敏感操作审计

具体方案：

1. 对数据集、分析任务、扫描任务、标注任务、预测任务、模型、报告、图表、聊天会话、备份和文件逐项配置资源归属校验。
2. 用户 A 不能通过修改 ID 访问用户 B 的资源；返回 403 或不泄露资源的 404。
3. 图表推荐、图表生成、预测查询/删除、标注查询、标签管理和报告查询不能只依赖登录鉴权。
4. 所有上传、下载、导出、脱敏、扫描、标注、审核、仲裁、预测、重训、模型回滚、报告生成和 AI 工具调用必须审计。
5. 审计包含用户、租户、资源、动作、路径、IP、traceId、结果和失败原因。
6. 禁止把密码、身份证原文、手机号原文和完整 AI 上下文写入日志。
7. 注册和用户查询统一使用不含 password 的 DTO，当前已完成的 DTO 改动必须保留并增加测试。

## 三、P1 合同能力优化

### P1-1 数据标注质量闭环

需要补齐：

- 标注任务分配、批次和优先级；
- 初标、复核、质检、仲裁、发布状态；
- 多人一致性、金标准样本和抽检；
- 标签范围、必填、互斥和格式校验；
- 返工、纠偏、标注员准确率、通过率和处理时长；
- 规则/模型来源、版本、原始标签、置信度和人工修改记录；
- 结构化数据、文本、图片、视频各自的支持边界和导出格式。

验收：创建任务后能完成预标注、人工提交、审核、仲裁、质量评分和发布，所有状态真实落库。

### P1-2 市场需求预测

已有本地线性回归、移动平均、指数平滑和 Holt-Winters 基础算法，但还要补齐：

- 时间字段、目标字段、日期格式、缺失值和样本量校验；
- forecastDays、算法、窗口、置信区间等参数；
- 训练集/验证集切分或滚动交叉验证；
- MAE、RMSE、MAPE、R2 的真实验证集指标；
- 模型版本、参数、训练范围、数据版本和效果对比；
- 预测失败原因、重训、回滚和历史版本；
- 模型部署、上线、下线和回滚流程。

验收：使用合法需求时间序列创建任务，返回真实预测结果和验证集指标；使用非法日期时返回明确 4xx，不返回 500。

### P1-3 图表、报告和趋势洞察

需要补齐：

- 趋势对比、分组对比、异常点定位和根因分析；
- 图表字段动态选择和筛选联动；
- 报告结论全部来自真实质量、安全和预测结果；
- 报告导出 PDF/Excel；
- 报告和图表权限；
- 报告依赖任务失败时显示 FAILED 和失败原因，不生成固定结论。

### P1-4 AI 工具真实闭环

代码中已有 `@Tool` 和工具注册结构，还需要验收证据：

1. 使用 Mock AI Provider 验证质量分析、安全扫描、图表和预测工具确实被调用。
2. 使用真实 DeepSeek Key 完成人工测试。
3. 工具参数包含 datasetId 时，必须执行资源权限校验。
4. 工具返回结构化数据，AI 只能解释真实返回值。
5. 没有 AI Key 时，上传、质量分析、安全扫描和预测等非 AI 功能必须正常启动。

## 四、P1/P2 性能、稳定性和安全验收

### 1. 性能测试

建立 JMeter、k6 或 Gatling 测试脚本，至少覆盖：

- 200 并发用户登录、查询和页面接口；
- 普通接口 P95 响应不高于 1.5 秒；
- 复杂任务提交响应不高于 5 秒；
- 百万级数据分析；
- 大文件上传和异步解析；
- 千万级标注查询分页。

报告必须包含硬件配置、数据量、并发数、P50/P95/P99、错误率、吞吐量和瓶颈分析。

### 2. 安全测试

补充：

- 依赖漏洞扫描；
- SAST/DAST；
- SQL 注入、越权、路径穿越、恶意文件上传；
- 暴力登录、限流、批量导出和敏感日志泄露；
- TLS 传输加密；
- 敏感数据加密存储；
- 密钥轮换；
- 备份、异地备份和恢复演练；
- 等保二级或以上的差距评估材料。

### 3. 质量门禁

在 Maven 中接入 JaCoCo，并设置：

- 总体覆盖率不低于 80%；
- 关键业务包覆盖率 100%；
- `mvn clean verify` 失败时禁止交付；
- 测试必须包含单元、集成、API、前端关键流程、性能和安全测试。

## 五、部署和交付文档

必须形成并交付：

- 需求规格说明书；
- 系统架构设计文档；
- 数据库设计和迁移文档；
- REST API/OpenAPI 文档；
- 前端构建和后端编译说明；
- 测试计划、测试用例、测试报告和缺陷记录；
- Docker/Compose 部署手册；
- 环境变量模板，禁止真实密码入库；
- 监控、告警和日志方案；
- 备份恢复和故障应急预案；
- 用户操作手册、运维手册和培训材料；
- 验收测试数据、验收记录和性能安全报告。

## 六、最终验收准入条件

以下条件全部满足后，才可进入合同最终验收：

1. `mvn clean verify` 成功；
2. 真实安全扫描不再 500；
3. 质量分析正确识别重复、空值、非法日期、离群值和负数；
4. 上传、解析、质量、安全、脱敏、图表、标注、预测、报告和审计完成真实闭环；
5. 双用户越权测试全部通过；
6. AI 工具完成 Mock 和真实 Key 两套验证；
7. 覆盖率、性能、安全、备份恢复和 Docker 报告齐全；
8. 前后端和生产 static 只有一个可交付版本；
9. 全部合同交付文档齐全；
10. 甲方可以在全新环境独立编译、部署和运行系统。

最终判断：当前版本可以继续最后一轮整改，但还不能认定为满足 River_AGI系统软件开发合同_v4 的全部功能、技术、性能、安全、质量和交付标准。
